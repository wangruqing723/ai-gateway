## 1. 目标、边界与现状

### 1.1 使用场景

个人开发者在可信本机管理多个 ChatGPT OAuth 账户，用这些账户为一个或多个提供商提供凭据。管理面需要先回答“为什么不能用、影响哪些提供商、怎样安全恢复”，再提供批量维护和可选调度。

不增加新的上游授权方式，不假定任何套餐一定支持某个模型、额度窗口或非公开能力。本次没有核验新的上游 API，不能把内部接口草案描述成 OpenAI 官方能力。

### 1.3 不变约束

- OAuth 提供商仍只能使用绑定账户，不回退到客户端 API Key。
- 现有单账户绑定关系保持：一个提供商绑定一个账户，一个账户可以被多个提供商引用。
- 本路线图不新增“一个提供商内部自动切多账户”的账户池；切换通过现有显式路由候选完成。
- 现有第三方导出格式保持兼容，本地元数据只进入独立原生备份。
- 普通列表、诊断、事件、预检和错误不返回令牌、密码或原始响应正文。
- 路由候选尝试、重试、熔断和已提交响应的转移边界保持可解释，不因账户层加入而重复计数。
- 不覆盖根级 PRODUCT.md、DESIGN.md、GLOSSARY.md、ADR 或已归档需求；本需求仅链接其约束。

## 2. 状态、身份与事务

### 2.1 状态必须分维度

现有 `status` 保留原兼容含义。新增视图分别描述以下事实，不把所有问题压成“可用/不可用”。

| 维度 | 拟表达内容 | 证据与限制 |
|---|---|---|
| 授权 | 访问令牌当前有效、可尝试刷新、需要重新授权 | 本地凭据及已知刷新结果；可刷新不等于下一次一定成功 |
| 管理 | 启用或暂停 | 用户显式设置；不由网络错误自动修改 |
| 用量查询 | 未查询、成功、失败，快照是否过期 | 分开保留最近尝试和最近成功时间 |
| 实际调用 | 未知、最近成功、最近失败 | 真实上游尝试；保留提供商、模型、来源和观测时间 |
| 准入 | 可准入、暂停、授权阻断、冷却或资源等待 | 第五阶段加入；与提供商熔断分开 |

访问令牌到期、OAuth 授权时间、订阅截止时间和额度重置时间是不同事实，不能互相推算。

用量缓存失败保留旧成功数据。页面显示数据年龄，不能因为最近尝试刚发生而把旧快照显示成新数据。额度重置时间到达只表示需要复核，不直接填回满额。

OAuth 提供商本地检查可显示“凭据条件满足，实际调用尚未验证”。只有明确的实际调用结果能显示对应模型近期调用成功。

第一阶段实现时确定的细节，契约见 [API_SPEC.md 2.1](API_SPEC.md#21-第一阶段已实现的字段)：

- **刷新失败和调用结果只在运行期保存。** 它们不写入账户文件，重启后回到未知，避免旧进程的结论冒充当前状态。
- **调用结果按尝试序号排序。** 每次真实尝试在取令牌前领取序号，只有序号更大的结果才能覆盖。旧请求迟到的成功不能盖掉更新的失败。
- **重新授权设置调用下限。** 低于下限的在途结果直接丢弃。账户删除后重建也不会继承旧结果。
- **调用记录同时按账户和按提供商保存。** 提供商健康只读该提供商自己的记录。同一账户经另一个提供商成功，不证明本提供商可用。
- **提供商健康新增 `unverified` 档位**，表示凭据可用但尚未实测。成功响应头之后的流中断单列为 `stream_interrupted`，与参数类 4xx 区分。
- **调用方主动取消的刷新不记为刷新失败。** `invalid_grant` 仍按原逻辑标记需要重新授权，并写入账户文件。
- **上游已轮换刷新凭据、但本地写盘失败时**，新凭据保留在内存并标记 `credentialsUnsaved`，同时向调用方返回错误。下一次任意成功写盘会一并写入新凭据。不能回滚上游已发生的轮换。
- **锁顺序为先账户表锁、后调用记录锁。** 写回调用结果只取调用记录锁，不排在账户文件写盘之后。

### 2.2 身份与凭据版本

- 本地账户 ID 是绑定、UI 选择和账户统计的稳定身份。
- 上游账户 ID 用于导入冲突匹配；邮箱、套餐、标签、排序位置均不能用于自动合并。
- 导入中的声明和显式账户 ID 不一致时阻止更新。解码 JWT 仅得到候选元信息，不等于验证签名或账户所有权。
- 普通令牌轮换保留账户身份、本地元数据和暂停状态，不清除已有额度冷却。
- 外部凭据替换和重新授权使用新的凭据世代，隔离替换前的刷新写回、冷却结果和恢复事件。
- 同一世代内的令牌轮换另有内部令牌版本，防止预检后产生的新令牌被旧导入覆盖。
- 对用户可见的版本只使用不含秘密的随机或不透明标识；不发布可用于离线猜测凭据的明文哈希。

### 2.3 账户版本与配置版本分离

拟新增账户控制版本，用于新增、删除、标签备注、暂停及显式凭据替换。用量轮询和运行计数不频繁改写这个版本。

自动令牌轮换仍需要内部凭据版本检查。导入计划和恢复计划除账户控制版本外，绑定目标凭据版本和必要的配置版本。计划内相关账户被并发修改时重新预检，不能用陈旧计划覆盖新状态。

涉及提供商绑定的操作沿用配置串行事务和配置 ETag。账户操作不假借配置版本表达自己的全部状态。

### 2.4 持久化与并发

继续采用有权限限制的账户存储和原子文件替换，但应使事务能够注入落盘故障测试。更新成功后才对读路径发布新快照；失败恢复原内存和原磁盘语义。

对 OAuth 刷新而言，上游可能已轮换 refresh token 后本地落盘才失败。此情形不能谎称上游副作用已回滚，应保留可用新凭据或明确进入可恢复错误状态，并由专项测试定义结果。不能用“批次已回滚”概括所有包含上游交换的操作。

锁顺序要在相关阶段明确定义。配置事务、账户事务和按账户刷新锁不能逆序获取。网络请求期间不持有全局账户写锁；凭据写回必须再次检查身份和版本。

### 2.5 解绑保存缺陷

普通配置保存与配置层采用相同空引用语义：

- 提供商已停用且 `accountId` 为空时允许保存。
- 提供商启用时必须有有效账户引用。
- 非空账户引用即使提供商停用也应指向现有账户，不把错拼的 ID 静默忽略。
- 本修复不自动启用、删除、解绑其他提供商，也不改变 OAuth 认证格式限制。

## 3. 凭据维护与诊断

### 3.1 导入预检与显式更新

保留旧导入接口的默认全批次校验、重复跳过和原子新增语义。新的预检/应用流程是独立能力，旧接口不能通过遗漏确认参数获得更新行为。

流程：

1. 在现有文件或文本入口提供源数据，只保存在本次流程内存。
2. 后端只读解析全部条目，输出安全元信息、匹配身份、建议动作、错误和影响提供商。
3. 新账户默认建议新增，已有账户默认跳过。用户可以对身份一致的已有账户显式选择更新。
4. 改变输入或选择后使旧预检失效，重新预检后才能应用。
5. 后端把原文字节、规范化选择、账户版本、相关凭据版本和有效期绑定到不含原文的签名计划。
6. 应用时重新解析和检查计划，在事务内一次提交。本批次不留下半更新。
7. 最终成功、失败、取消、关闭或切离流程时清理文件、原文和计划。

预检与最终应用之间暂时保留输入是两步流程的必要状态，不写浏览器持久化存储。预检不是最终提交，不能套用旧单步“任何请求结束即清空全部输入”造成无法应用。最终应用结束仍沿用清理原则。

需要更新的字段是明确的一组凭据及可由它们获得的账户元信息。缺失字段不得暗中与旧凭据拼接，除非文档审阅后定义了具体允许的保留规则。标签、备注、暂停状态、首次授权时间和绑定关系必须保留。

同一批次出现多个上游身份相同的记录时展示重复关系，不采用隐式最后写入胜出。默认兼容旧跳过口径；同时请求多次更新同一目标时阻止应用。

不依据文件的 `last_refresh` 自动证明新旧凭据顺序。对于疑似旧文件只作提醒，自动刷新后版本发生变化的目标必须重新预检。

第二阶段实现时确定的细节，契约见 [API_SPEC.md 3.3](API_SPEC.md#33-第二阶段已实现的导入契约)：

- **更新整组替换凭据。** ID 令牌、访问令牌、刷新凭据、到期时间和最近刷新时间都取自导入记录，不与旧值拼接。邮箱和套餐只在文件提供时更新。
- **保留本地信息。** 本地 ID、首次授权时间、标签、备注、用量快照和 Provider 绑定保持不变。
- **更新属于外部凭据替换。** 推进凭据世代，清除刷新失败记录，并按 2.1 的调用下限隔离旧凭据的在途结果。
- **在途刷新不能覆盖新导入。** 刷新写回前比较凭据世代，世代变化时丢弃交换结果；替换后的访问令牌仍有效则直接使用。
- **计划摘要绑定目标凭据世代。** 预检之后发生的普通令牌轮换也会让应用失败，要求重新预检。
- **无效条目阻止应用。** 用户必须对无效条目显式选择跳过，不默认部分导入。

### 3.2 分层诊断

| 步骤 | 行为 | 副作用与代理 |
|---|---|---|
| 本地检查 | 检查绑定、授权状态、到期时间、暂停和历史结果 | 无出网，不证明模型调用成功 |
| 刷新链路 | 获取可用令牌；强制刷新是额外显式选项 | 可能轮换并保存令牌；管理入口默认使用 OAuth 管理客户端 |
| 用量查询 | 使用当前受支持的用量查询路径 | 使用 OAuth 管理客户端；失败不等于账户整体失效 |
| 实际调用 | 对明确提供商和模型发起最小测试请求 | 使用该提供商客户端和请求期刷新路径；会消耗额度，必须确认 |

管理请求使用专用 OAuth 代理或全局回退。模拟提供商路径时必须明确提供商，沿用该提供商代理。结果只报告代理来源类别，不暴露代理 URL 密码。

诊断使用短总预算、有界响应和可取消 context，不自动遍历全部模型、不连续压测、不因一个诊断失败触发全账户重试。实际调用诊断不在打开页面、刷新列表或健康轮询时自动执行。

只按有证据的范围给出结论：特定模型失败不等于全部模型失败；usage 返回鉴权错误不直接证明 refresh token 失效；明确 `invalid_grant` 等授权证据才触发重新授权。

第二阶段实现时确定的细节，契约见 [API_SPEC.md 4.1](API_SPEC.md#41-第二阶段已实现的诊断契约)：

- **本地检查总会执行。** 它只读状态，可以给后续出网步骤提供阻断依据。
- **预算耗尽按取消处理。** 诊断用带原因的取消而不是超时截止，避免把诊断自己的时间上限当成网络超时写进用量快照或调用记录。
- **等待账户锁可取消。** 刷新锁和用量锁改为可随 context 取消的互斥锁，诊断不会因为同账户的长时间刷新或查询而越过总预算。
- **实际调用写回最近调用记录。** 这是一次真实上游调用，账户和 Provider 健康据此更新；但不写请求日志和指标，不上报熔断器。
- **诊断不输出原文。** 实际调用关闭网关日志里的上游错误正文和调试抓包，响应只含固定文案和类别。
- **停用的 Provider 跳过。** 诊断不绕过启停设置。熔断开路时仍发起一次调用，并在结果中注明。
- **最大输出受压制。** 测试请求上限 256 token，Provider 配置的 maxTokens 更大时也按该值压低。

前端入口在账户行操作列。浮层只使用已保存配置中的绑定，实际调用需要单独勾选额度消耗确认，改变目标即清除确认。取消只停止等待，界面说明已发生的令牌交换和调用不会回滚。

## 4. 账户管理与交互

### 4.1 账户暂停

拟在账户记录增加管理启停状态，缺失时兼容为启用。有效使用条件同时取决于账户启用、提供商启用、凭据和准入状态。

暂停不改写提供商 `enabled`，不清空绑定。恢复只解除账户层暂停，不启用用户单独停用的提供商。页面并列显示“提供商配置启用，但账户暂停”，避免状态冲突。

建议已提交的请求继续完成，未获得准入的等待者被唤醒并跳过。具体在途处置以 D01 确认为准。至少在候选检查和实际发出前都要校验，避免等待期间暂停后仍发请求。

### 4.2 筛选、排序与选择

保留现有关键词搜索，追加独立筛选维度：授权、管理启停、近期调用、绑定、套餐和标签。多个维度按明确的组合规则筛选，不改变账户数据本身。

排序只改变管理页面：默认保持稳定顺序，提供按指定用量窗口剩余比例、重置时间和最近成功时间的选择。未知和失效数据单独标识并稳定置后；相同值以邮箱和本地 ID 稳定排序。

显示可用的真实用量窗口让用户选择，不硬编码套餐必然具备的窗口。代码审查窗口和其他额外窗口不能直接作为普通模型排序依据。

“选择当前筛选结果”与“选择全部账户”是不同动作。隐藏的已选择账户明确显示数量和清除入口。后台刷新、账户删除或排序变化不把选择转移到相同列表下标的新账户。

第三阶段冻结细节（契约见 [API_SPEC.md 5](API_SPEC.md#5-暂停与批量操作)）：

- **暂停字段。** 账户文件写 `paused` 和 `pausedAt`，缺失按启用。视图输出 `enabled` 与 `pausedAt`。第三方导出不带它们。
- **唤醒等待者。** 每个账户维护暂停监听表。尝试在取得令牌前登记监听，排队等待使用派生 context；暂停提交后按原因取消这些 context，被唤醒的尝试记为账户暂停跳过。令牌交换仍使用请求自身 context，避免中途取消导致已轮换的刷新凭据丢失。
- **锁顺序。** 暂停写入持有账户表写锁，再取监听锁取消等待者；登记监听持有账户表读锁再取监听锁，保证不会漏掉在检查与登记之间发生的暂停。
- **筛选组合。** 关键词、授权、管理状态、实际调用、绑定、套餐、标签七个维度之间 AND；标签多选之内 OR。筛选只在页面内存中，不持久化。
- **排序。** 默认按邮箱和 ID。可选主窗口或次窗口剩余比例、该窗口重置时间、最近实际调用成功时间，可切换升降序。没有该窗口、快照不新鲜或重置待复查的账户视为未知，不论升降序都排在最后；相同值按邮箱和 ID。额外窗口和代码审查窗口不参与排序。
- **最近成功时间。** 第三阶段只用最近一次真实调用为成功时的观测时间；最近一次是失败时视为未知。第四阶段账户统计接入后改用统计中的最后成功时间。

### 4.3 批量操作

- 只读或出网刷新返回逐项结果，单账户失败不遮蔽其他结果。
- 标签批量更新使用明确“添加/移除”语义，不覆盖每个账户不同的备注。
- 暂停、恢复、标签和删除先预检，再在账户文件内一次提交；绑定变化使危险计划失效。
- 被任何提供商引用的账户不能删除，包含已停用的提供商。删除不自动解绑。
- 原子性仅适用于本地账户变更；用量查询无法撤销已经发出的出网请求，结果应如实逐项报告。

### 4.4 页面结构与质量约束

沿用仓库现有深色、青色强调、中文文案和本地字体。账户列表仍位于提供商页，不新增顶层导航，不重做全页设计系统。

- 列表优先展示身份、授权/暂停、用量快照、绑定和主动作。
- 长备注、诊断详情、统计和事件采用展开详情，避免在每行堆所有字段。
- 批量操作栏只在选择存在时出现，并明确对象和影响。
- 导入预检沿用统一导入导出弹窗。加密备份是独立模式，不改变第三方格式的含义。
- 诊断和用量查询展示可区分的加载状态，失败保留旧内容及最近成功时间。
- 窄屏让次要信息折叠或换行，不靠缩小字号挤入桌面表格。
- 浮层避开滚动容器裁剪，键盘焦点、Esc 和关闭后焦点恢复保持一致。
- 请求进行中防重复提交；取消语义明确，不能宣称前端关闭已经回滚服务端事务。
- 所有状态有文字，不只用颜色。统计必须有样本量和窗口，未知数据不是零。
- 重建 HTML 与 CSS 两种产物，并复用现有字体已有图标，避免名称退化成文字。

第三阶段批量实现细节：

- 批量预检与应用复用导入流程的签名凭证机制，但使用独立派生密钥，两类凭证不能互相冒用。
- 计划指纹包含操作、规范化标签、逐项账户 ID 与动作前后值，以及配置版本。任何一项变化都要求重新预检。
- 批量用量刷新沿用单账户刷新逻辑与锁，同一进程同时只运行一批，总预算耗尽按取消处理。
- 页面选择以账户 ID 保存。列表刷新后丢弃已不存在的 ID；被筛选隐藏的已选账户单独计数，提交前在确认中列出数量。

## 5. 观测、事件与提醒

### 5.1 账户统计口径

真实调用发出时捕获本地账户 ID、凭据世代、提供商、模型和来源。不能在请求完成时查当前绑定反推账户，否则换绑会把旧请求记到新账户。

顶层客户端日志仍每请求一条。账户统计采用真实上游尝试口径：每次本地重试和故障转移分别计入实际使用的账户。暂停、冷却、构建或队列跳过不计入真实调用数。

成功按转发完成结果判断，不能只看 2xx 响应头。流中断、活跃超时和转换失败要保留失败结论。诊断调用与用户模型调用分开；OAuth 刷新和用量查询不计入模型调用成功率。

提供窗口调用数、成功率、延迟、限流次数和最后成功时间。延迟说明是上游尝试耗时还是包含排队的客户端耗时，不混用既有顶层首字指标。

窗口统计沿用有界桶和直方图原则，不从请求日志环反复重算。累计只承诺当前进程，不推算历史；账户删除后清理其统计对象，旧日志保留当时身份但不关联到后来重建的账户。

这是网关观测，不是上游订阅账本。不同用量窗口、credits 和模型调用数分开展示，不用请求次数推算余额或账单金额。

### 5.2 运行事件

扩展现有有界内存事件流，增加可选账户维度。事件包括重新授权要求、刷新链路失败、凭据显式更新、绑定变化、暂停恢复、共享冷却和有证据的恢复。

每种异常在状态转移时触发，不在每次轮询重复添加。成功刷新可解除刷新错误，但不代表模型调用恢复；用量成功可解除查询错误，但不清除额度冷却。

恢复事件必须来自异常之后的新请求或新观测，并检查凭据世代和请求序号。旧在途请求的迟到成功不能覆盖较新的失败状态。冷却到期可记录等待结束，不标记调用恢复。

事件默认沿用内存容量和进程生命周期，不在本需求中偷偷新增无限持久化审计日志。若用户希望持久化事件，应另行确认保留周期和敏感数据范围。

### 5.3 提醒与外部通知

先提供页面内状态提醒。低额度提醒只依据新鲜且适用的窗口；窗口未知或已过期不产生“额度恢复”通知。

浏览器系统通知和外部通知渠道属于 D02，不能未经选择自动启用。外部发送前必须明确目的地址、消息字段、认证方式和失败重试边界。

通知 payload 只包含已批准的安全元信息和状态，不含令牌、密码、提示词、工具输入、代理凭据或上游正文。通知失败不能阻塞转发，也不能无限重试。

### 5.4 第四阶段实施契约

以下口径在第四阶段实施前冻结，依据为 D02 及 T21 的已批准推荐方案。

**尝试归属。** OAuth 候选进入准入前，以请求开始时的 Provider 快照取本地账户 ID，写入尝试明细 `accountId` 及统计对象。请求途中换绑只影响之后的请求。统计挂在账户内存对象上：删除账户即释放；删除后重建的账户 ID 不同，不继承旧统计；重新授权和显式导入更新保留统计。

**统计窗口与口径。** 窗口复用 `metrics.windowMinutes`，热重载生效；按分钟分桶，边界精度为一分钟，固定最多 61 桶，首次写入时才分配。累计只覆盖当前进程。

- 真实调用：已向上游发出且得到结论的尝试，含本地重试和故障转移；本地重试另计子项。客户端在上游响应前断开时没有结论，不计数。
- 成功率 = 成功 / 真实调用，判据与「最近实际调用」相同，流中断和转换失败计为失败。
- 限流：结论为 HTTP 429 的真实调用。
- 延迟：上游响应头延迟，从发出请求计到收到响应头，不含排队和正文生成；没有响应头的尝试不进入样本。
- 准入跳过：账户暂停、取令牌失败、队列等待失败分三类计数，不计入真实调用。
- 诊断调用单列成功与失败，不进入真实调用、成功率和延迟。
- 管理请求：OAuth 刷新交换和用量查询分别计成功、失败，不进入模型调用统计。
- 没有样本时成功率和延迟为 null，不以 0 代替。

**账户事件。** 运行事件增加可选 `accountIds`（单账户事件只有一项）与 `account` 显示名，沿用 100 条共享环形缓冲，不持久化。事件只在状态转移时写入：

| 事件 | 触发 |
|---|---|
| `account_reauth_required` | 刷新凭据被拒，账户首次进入需要重新授权 |
| `account_refresh_failed` | 刷新失败（非凭据失效）；连续失败只记一次 |
| `account_refresh_recovered` | 有失败记录后刷新成功；只说明刷新链路恢复，不代表模型调用恢复 |
| `account_credentials_updated` | 重新授权或显式导入更新；批量导入合并为一条 |
| `account_binding_changed` | 配置生效后 Provider 绑定账户变化，每个 Provider 一条 |
| `account_paused` / `account_resumed` | 单个或批量暂停、恢复；批量合并为一条 |
| `account_recovered` | 授权或刷新异常后经凭据替换，之后新发出的真实或诊断调用首次成功 |

替换前已发出的调用迟到成功不触发恢复，冷却或时间流逝也不触发恢复。事件只含固定文案、账户 ID、邮箱和 Provider 名称，不含令牌、上游正文、提示词或代理凭据。

**页面提醒。** 账户区显示「需要关注」列表，来源为需要重新授权、自动刷新失败、凭据未保存、额度偏低及近期恢复事件。额度偏低指快照新鲜、窗口不在待复查状态、剩余比例不高于 10%；这是本阶段的实现阈值。已读状态按「条件 + 证据时间」存于浏览器本地，最多 200 项；失败时间或重置时间变化后重新提醒。不使用浏览器系统通知，不发送外部通知。

实现中的证据口径（2026-11-04 落地）：

| 提醒 | 证据 |
|---|---|
| 需要重新授权 | 凭据最近更新时间与到期时间。刷新失败时间只在进程内存在，重启后会变，不能作已读依据 |
| 自动刷新失败 | 最近一次刷新失败时间 |
| 新凭据未保存 | 凭据最近更新时间 |
| 额度偏低 | 账户、窗口名与该窗口重置时间 |
| 近期恢复 | 事件种类、时间与事件 ID；只取 `recovered` 为 true 且账户仍存在的事件 |

已读上限满时先淘汰已不再出现的条件，保留仍有效提醒的已读记录。定位提醒到被筛选隐藏的账户时只提示，不改动筛选条件。

## 6. 准入、共享冷却与可选调度

### 6.1 账户共享资源层

共享身份以绑定的本地账户为基础；导入身份去重防止同一上游账户以重复记录规避约束。新增策略由账户级位置统一管理，不从多个提供商的不同设置随意推导共享值。

参数设计以 D03、D04 确认为准。未开启账户控制时保持原请求行为；零值和未配置必须区分，不把显式关闭静默改成默认。

联合准入必须同时考虑提供商资源和账户资源。只有两者可执行时才授予执行票据，等待中不占用另一资源。共享完整等待预算，取消、构建失败、切换和结束均幂等释放。

账户暂停和明确冷却尽早过滤；实际发出前再次验证票据、绑定快照和状态。没有真实请求的跳过不消耗 maxAttempts，也不调用上游失败上报。

### 6.2 共享冷却与失败范围

不能仅凭任意 HTTP 401/403/429 就断言全账户失效。分类要结合路径、可识别错误类别和真实失败范围，并使用受控测试夹具验证。

- 明确授权刷新失效进入重新授权状态。
- 明确账户级额度或限流作用于同账户全部提供商。
- 已知模型、端点、代理或提供商范围问题不能升级为全账户永久封禁。
- 无法可靠识别的错误保留原提供商失败与重试语义，不伪造上游能力。
- 有效 Retry-After 决定相应等待；本地默认退避不得截短上游要求。
- 成功请求、普通令牌轮换或配置保存不自动取消明确的额度冷却。
- 凭据世代和请求序号防止旧请求写回新账户状态，延迟成功不解除更新后的异常。

熔断仍按现有每候选最终结果上报。账户级授权、暂停和冷却是独立准入原因，不把本地背压或凭据状态当成提供商网络故障。

没有候选可调用时分别汇总停用、账户暂停或授权阻断、冷却、熔断和其他原因。新增终态优先级须与原有全停用、无密钥、熔断、限流、上下文及转换错误表一起审阅，不能随意覆盖现有终态。

### 6.3 额度感知与粘性

新排序是显式选择，不改变现有 failover、round-robin 和 least-queue 的默认语义。新策略或可选排序层的形态由 D05 确认。

候选排序只读取安全额度与运行快照，不在选择期间临时查询 usage，也不丢候选。适用窗口、缓存年龄和排序依据必须可解释。

已有成功会话在目标可准入时继续粘住它，不仅因为另一个账户剩余比例更高就换绑。目标暂停、授权阻断或明确冷却时才让正常转移机制工作。只有成功后更新粘性。

粘性身份需要考虑提供商换绑账户：同名提供商与模型被换到账户后不能误认为仍命中原账户的缓存身份。热重载只失效真正变化的目标，保留未变化的会话。

策略不创建额外额度，不跨越上游限制，不改变 failover 是否启用和最大真实尝试语义，客户端已经收到响应后禁止切换。

### 6.4 第五阶段实施契约

以下口径在第五阶段实施前冻结，依据为 D03、D04、D05 的已批准推荐方案。字段名与阈值是实现取值，随阶段汇报请用户确认。

**账户共享约束（T26、T27）。** 顶层新增 `chatgptAccountLimits`，对每个 OAuth 账户各自建一个共享桶，同一账户绑定的全部 Provider 共用：

- `maxConcurrent`：`*int`，未配置表示不限制；显式值 1–100，写 0 报错。
- `maxPerSecond`：整数 0–100，0 或未配置表示不限制，与 Provider 同名字段口径一致。
- 两项都不限制时完全不启用联合准入，请求路径与改动前相同。未提供逐账户覆盖，所有账户共用同一组上限。
- 直通模式（D04）继续跳过本地排队，因此账户并发和速率不生效；显式开启的共享冷却仍然生效。

联合准入：账户桶持有一条按到达顺序的等待队列，只有账户与 Provider 同时有空位时才一次授予执行票据，等待期间不占用任何一方的槽位。账户内按到达顺序挑选第一个其 Provider 也能准入的等待者，被忙碌 Provider 挡住的请求不阻塞同账户其他 Provider。Provider 自身已有普通等待者时，联合准入不插队。账户等待与 Provider 等待共用该 Provider 的 `maxQueueWait`；取消、超时、暂停唤醒和结束都幂等释放两层槽位。热重载只影响之后的准入判断，不打断在途请求；限制被移除后，残留等待者按不限制处理。

**共享冷却（T28）。** 顶层同一段新增 `sharedCooldown`，布尔值，默认 false。开启后：

- 触发：OAuth Provider 的真实上游响应为 HTTP 429，且错误正文 `error.type` 为 `usage_limit_reached`。其他 429、401、403 或无法识别的错误不升级为账户冷却，保留原有 Provider 失败与重试语义。
- 时长：取 `resets_at`、`resets_in_seconds`、`Retry-After` 中最晚的一个；都没有时冷却 60 秒；上限 30 天。本地默认值不截短上游要求，新的报告只延长、不缩短已有冷却。
- 范围：整个账户，覆盖该账户绑定的全部 Provider，只在当前进程内存中，不写账户文件。
- 结束：到期、手动解除、关闭 `sharedCooldown`、删除账户或进程重启。成功请求、令牌轮换、重新授权和普通配置保存都不解除。
- 隔离：手动解除时记录请求序号下限，解除前发出的请求迟到的 429 不会重新冷却。
- 准入：候选循环在熔断判断之前跳过冷却中的账户，记 `account_cooldown`，不消耗 `maxAttempts`、不调用熔断。排队中的等待者在冷却生效时立即被唤醒放弃。触发冷却的那次请求若冷却时长超过 `failover.maxRetryAfterMs`，按长限流的免费尝试处理，并且不在同一账户上本地重试。
- 终态：没有任何真实请求且存在冷却跳过时返回 429 `account_usage_limited`，`retry-after` 取最早到期时间。优先级排在 `no_selectable_provider_key` 之后、`breaker_open` 之前。
- 事件：进入冷却记 `account_cooldown`，手动解除记 `account_cooldown_cleared`；到期不记事件，也不标记恢复。

**额度感知排序（T29）。** 路由新增 `quotaAware`，布尔值，默认 false，只对多候选路由有效，单候选写 true 报错。它是叠加在既有策略之后的稳定分层，不是新策略：

- 只读取页面同源的内存用量快照，不在选择时发网络请求，也不丢候选。
- 只认普通模型的 primary 与 secondary 窗口；快照不新鲜、窗口待复查或缺失视为未知。任一窗口剩余为 0 归为「已耗尽」，任一窗口不高于 10% 归为「偏低」，其余及未知归为「正常」。
- 排序为正常、偏低、已耗尽三层，层内保持原策略顺序。非 OAuth 候选视为正常。
- 粘性命中的目标在可准入时保持在队首，不因其他账户剩余更多而换走；它暂停、授权阻断或冷却时由原有跳过逻辑让后续候选接手。粘性只在成功后更新。
- 粘性身份改为包含绑定账户：同名 Provider 与模型换绑到其他账户后不再命中旧映射，未变化的目标保留映射。

**观测（T30）。** 账户视图新增可选 `cooldownUntil`；账户统计接口新增 `admission`，含联合准入是否启用、在途与排队数、上限和冷却截止。准入跳过统计新增 `cooldown`。运行事件与请求日志尝试明细新增 `account_cooldown`。

## 7. 后台刷新与双实例安全

后台功能的默认开关、活跃定义和各项周期由 D07 确认。倾向先默认关闭，明确启用后只调度近期使用、未暂停且不需重新授权的账户。

令牌预刷新复用已有按账户互斥；请求路径、人工诊断和 worker 竞争同一账户时不能并行交换同一 refresh token。用量查询采用有界 worker、时间错开、缓存复用、错误退避和上游 Retry-After。

按 context 管理循环生命周期，热重载取消旧计划并重新协调，关闭服务时取消等待和出网。只修改调度时间不重新计算已有冷却截止时间。

当前开发与正式实例共用账户文件，需要先解决 D06：

| 可选方案 | 必须满足的条件 | 代价 |
|---|---|---|
| 跨进程协调 | 稳定锁对象、完整读改写链路和令牌交换协调；重新读取新版本，处理进程退出 | 实现和平台测试较多 |
| 明确单写者角色 | 只有指定实例可更新、刷新和后台写入；非写者读取行为明确 | 两实例使用能力受到限制 |
| 隔离账户存储 | 经用户确认改变共享关系，明确迁移与同步方法 | 不再保留当前共享账户意图 |

只给临时文件 rename 加锁不够。两进程可以先读到相同旧凭据，再依次写回或交换；必须协调读、上游副作用和最终提交。

双实例回归使用独立临时账户库。未选定并验证方案前不修改 Compose，也不启用共享库后台写入。

### 7.1 第六阶段实施契约

以下口径在第六阶段实施前冻结，依据为 D06、D07 的已批准推荐方案。字段名、周期与上下界是实现取值，随阶段汇报请用户确认。

**跨进程协调（T32，D06）。** 保留开发与正式实例共享 `data/chatgpt-accounts.json`。

- 锁对象是同目录下稳定存在、从不被替换的 `chatgpt-accounts.json.lock`，用 `flock` 排他锁；进程退出时由内核释放。2026-11-05 实测：两个容器绑定挂载同一宿主目录时互相阻塞。宿主机进程与容器内进程不在同一内核，不保证互斥，文档与配置注释写明不支持这种混合部署。
- 每个写入入口按「进程内存储锁 → 文件锁 → 读取并合并磁盘 → 修改 → 原子替换 → 释放」执行。合并以磁盘为准覆盖可持久化字段，保留进程内运行状态（统计、调用记录、冷却、准入监听）；磁盘上已删除的账户从内存移除，磁盘上新增的账户加入内存。本进程刷新成功但写盘失败的凭据（`credentialsUnsaved`）在合并时保留内存值，因为持锁期间没有其他实例能做更新的交换。
- 令牌刷新在账户级刷新锁内完成「重新读取 → 判断是否仍需刷新 → 交换 → 写回」。另一实例已经轮换过时直接使用新令牌，不再用旧 refresh token 交换。刷新锁是 `chatgpt-accounts.json.refresh/` 下按账户 ID 摘要命名的锁文件（同样 `flock`，不含凭据）：同一账户的交换在实例间串行，交换期间不占用全局存储锁，只在重新读取和写回时短暂持有，暂停、元数据、导入等写入不必等待最长 20 秒的交换。交换期间凭据被导入或重新授权替换时，写回按凭据世代放弃本次结果。（实施中调整：最初让交换持有全局存储锁，会让同时发生的暂停等到交换超时。）
- 只读路径不加文件锁：账户列表、准入监听、暂停判断和取令牌入口最多每秒检查一次文件身份，变化时用非阻塞方式加锁并合并，拿不到锁就跳过本次。其他实例的暂停因此在约 1 秒内生效，并唤醒本进程排队中的等待者。
- 等不到文件锁的写入在 30 秒后返回存储忙错误，不写入任何内容。不支持 `flock` 的平台只保留进程内互斥，并拒绝启用后台刷新。

**后台刷新（T33–T35，D07）。** 顶层新增 `chatgptBackground`，默认全部关闭：

- `tokenRefresh`：布尔。对活跃账户在访问令牌到期前 10 分钟预刷新，复用按账户刷新互斥与上面的跨进程刷新链路。
- `usageRefresh`：布尔。对活跃账户按 `usageIntervalMinutes`（30–1440，默认 30）刷新用量，按账户 ID 错开最多十分之一周期。
- `activeWindowMinutes`：5–1440，默认 60。活跃账户指本进程在该时长内为它发起过真实上游调用（不含诊断），且未暂停、不需重新授权、有 refresh token。闲置、暂停和需要重新授权的账户不产生后台请求。
- 单个 worker 循环，每 30 秒检查一次，每轮最多 10 个任务、并发 2，单任务 45 秒预算。热重载只更新设置并立即重算，不会出现第二个循环；全部关闭或网关关闭时取消等待和出网，并等循环退出。
- 失败退避：令牌从 1 分钟起指数翻倍，上限 60 分钟；用量从一个周期起翻倍，上限 24 小时；用量返回的 `Retry-After` 更长时以它为准，且任何入口拿到的 `Retry-After` 都会推迟后台的下一次。网络故障不标记重新授权，只有 `invalid_grant` 才标记。人工刷新、诊断和请求路径的按需刷新不受后台退避限制；任何入口的成功都清零失败计数。
- 两个实例都开启后台时，用量的最近尝试时间与令牌到期时间都来自共享文件，一方完成后另一方据此推迟，不重复请求。

**观测（T35）。** 后台开启时账户视图带 `background`：是否活跃、最近使用时间、令牌与用量各自的上次运行、结果、下次计划和连续失败次数；不活跃时说明跳过原因。新增 `GET /api/chatgpt/background` 返回循环是否运行、是否具备跨进程锁、最近一次检查时间。

## 8. 加密备份与恢复

原生备份和第三方凭据导出分开。第三方格式继续用于工具互操作，原生备份用于保留网关本地账户信息，不冒充完整网关实例备份。

### 8.1 格式约束

外层是可识别、版本化且有资源上限的加密容器，包含加密算法标识、密码派生算法与受限参数、随机盐、nonce 和认证密文。

使用成熟的认证加密与密码派生方法，具体算法、参数、依赖和密码输入方式由 D08 确认。算法标识和版本等外层字段必须纳入认证，不能允许密文被篡改后降级解释。

解密前检查版本、密文大小和密码派生资源参数，防止恶意文件造成无界 CPU 或内存消耗。认证失败返回统一安全错误，不给出明文片段。

### 8.2 备份内容

拟包含所选账户的凭据、上游身份、本地元数据、首次授权时间及可选订阅声明。管理暂停状态按恢复选择明确保留。

不恢复用量缓存、调用健康、冷却、统计、会话粘性、运行事件或正在授权的 session；这些数据只描述旧实例的暂时状态。

备份时不自动登录或刷新凭据。账户与其全部字段采用一致快照，密码不写盘、不进 URL、不进日志、不缓存。

### 8.3 恢复与绑定

恢复先解密预检，显示账户身份冲突、将新增或更新的项、元数据覆盖范围和绑定影响；不返回解密原文。

原有本地 ID 冲突时不能覆盖不同上游身份。更新已有账户保留其绑定，通过明确策略处理元数据；新增账户的本地 ID 采用经确认的保留或重映射规则。

D09 的推荐流程为先原子恢复账户，再输出安全的源本地 ID 至目标 ID 映射，供既有提供商/路由迁移使用。两个保存步骤分别报告结果，失败不能宣称整个恢复全成功。

如果最终要求连带恢复配置，应先设计跨文件事务和恢复日志，不用“先写账户再写配置”冒充原子操作。该选择目前没有批准。

敏感传输遵循 [本机敏感传输安全决策](../adr/0001-local-sensitive-transfer-boundary.md)：独立、显式、本机同源操作；普通查询仍不暴露凭据；不能把同源检查当成身份鉴权。

### 8.4 第七阶段实施契约

以下口径依据 D08、D09 的已批准推荐方案，于 2026-11-05 实施前冻结。数值是实现取值，随阶段汇报请用户确认。

**加密（D08）。**

- 加密使用 AES-256-GCM，12 字节随机 nonce。密钥由 PBKDF2-HMAC-SHA256 派生：16 字节随机盐，32 字节密钥，导出固定 600,000 次迭代。迭代次数依据 OWASP Password Storage Cheat Sheet 的 PBKDF2-HMAC-SHA256 推荐值，2026-11-05 核验。
- 模块声明 `go 1.23`，标准库 `crypto/pbkdf2` 从 1.24 起才有，`go vet` 会报错（2026-11-05 实测）。按 D08「拒绝未经批准的依赖升级」，不上抬 go 指令，也不引入 `golang.org/x/crypto`。PBKDF2 用标准库 HMAC 按 RFC 8018 实现，并用 RFC 7914 第 11 节的测试向量和 1.24+ 标准库实现交叉校验。
- 外层容器的格式、版本、算法、迭代次数、盐和 nonce 全部纳入 GCM 附加认证数据，改动任何一项都会认证失败。
- 解密前依次拒绝：超过 16 MiB、JSON 结构不严格、未知格式或版本、未知算法、迭代次数不在 100,000–10,000,000、盐或 nonce 长度不对、密文过短或过长。这些检查都在密钥派生之前完成。
- 密码错误与密文被篡改返回同一个错误，不区分。
- 导出密码至少 12 个字符；恢复只要求非空。两者上限都是 1024 字节，必须是合法 UTF-8 且不含 NUL，按原字节使用，不做 Unicode 规范化。
- 密码只放在本机同源 POST 的 JSON 正文中，不写盘、不进 URL、不进日志。浏览器只在弹窗打开期间保存密码，关闭或成功后立即清空。

**内容与恢复（D09）。**

- 明文载荷包含所选账户的本地 ID、上游身份、凭据、邮箱、套餐、授权与订阅时间、标签、备注、需要重新授权标记和暂停状态。
- 不包含用量缓存、调用记录、统计、冷却、后台状态、事件、OAuth 会话，也不包含 Provider 绑定。导出不刷新令牌。
- 恢复按上游身份匹配本地账户：
  - 本地没有该身份时默认新增。源本地 ID 空闲且格式合法时保留，否则生成新 ID，并在计划和结果中标出已重映射。源 ID 被另一上游身份占用时一律重映射，不覆盖。
  - 本地已有唯一同一身份时默认跳过，需要显式选择更新。更新整组替换凭据，保留本地 ID、绑定和用量快照。标签和备注按 `metadata` 策略处理：`keep` 为默认，保留本地值；`replace` 用备份值覆盖。暂停状态只在 `restorePaused` 为 true 时取备份值。
  - 本地有多个同一身份、备份条目缺少 refresh token 或无效时，只能跳过。
  - 备份凭据的刷新时间早于本地时提示「可能是旧备份」，因为旧 refresh token 可能已被轮换失效。
- 应用在一把写锁内重建计划，与预检一致才一次落盘；失败时整批回滚。更新视同外部凭据替换：推进凭据世代，清空旧凭据的刷新失败与调用记录。
- 结果返回源本地 ID 到目标 ID 的映射，覆盖新增、更新和匹配到唯一本地账户的跳过项。页面把映射交给既有的提供商／路由迁移导入，作为账户映射的预填值。账户恢复与配置迁移分两次保存，分别报告结果，不宣称跨文件原子。

## 9. 测试与迁移

先补基础专项，再随阶段扩展，所有新状态均兼容旧账户数据的字段缺失。状态省略、零值和未知值必须有测试，不能依赖真实账户固定套餐。

测试包括：

- OAuth 会话 state/PKCE、过期、错误或重复回调、并发回调。
- 刷新轮换、凭据替换竞争、刷新落盘失败和令牌身份变化。

- JSON/ZIP 多格式往返、路径和大小限制、重复跳过、显式更新和全批次失败。
- 绑定、幂等、解绑后普通保存、暂停恢复和批量删除竞争。
