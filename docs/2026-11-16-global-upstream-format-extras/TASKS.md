# 按上游格式注入全局请求头与请求体

状态：已实现，待用户验收。

创建日期：2026-11-16

## 目标

在“全局设置”增加按实际上游协议格式配置的请求头和请求体扩展项。它是可选的全局兜底：当局部 Provider／路由／目标配置没有同名项时，每一次真正发往模型上游的推理请求都必须按其上游格式带上对应的全局配置；不能只显示在页面或只写入配置文件而未进入真实转发请求。

现有 Provider / 路由 / 目标级 `extraHeaders`、`extraBody` 保持可用，并在同名冲突时优先。新的全局配置是跨 Provider 的默认兜底，适合配置同一种上游协议共同要求的私有头和私有请求字段。

## 验收标准

- 可分别为 `anthropic`、`openai`、`openai-responses` 配置全局附加请求头和请求体字段。
- 可分别为三种格式配置专用全局 User-Agent；每种格式按 Provider → 对应格式的全局值 → 客户端 UA → Go 默认值选择。
- 全局项可完全不配置；配置后，真实发往某格式上游的每次模型推理 POST（包括重试、故障转移、换密钥后的下一次请求）都会以它补足局部未配置的字段；其余格式绝不串用。
- 图片识别发出的 OpenAI Chat 请求也携带 `openai` 全局项；模型列表、健康检测等无请求体的 GET 不被伪造注入请求体。
- 全局项与既有 Provider / 路由 / 目标级扩展发生同名冲突时，局部项最终生效；全局项只作为兜底，不覆盖任何局部定制。网关维护的结构字段和鉴权/内容类型头仍不可覆盖。
- 既有 `Provider → Route → Target` 请求体叠加顺序、Provider 请求头写入位置，以及 ChatGPT OAuth 的后处理顺序均保持不变；仅在它们之前增加全局默认层。
- 既有请求头／请求体哪些字段可传、哪些字段被黑名单拦截的逻辑完全不变；全局项复用同一套校验与运行时拦截，不新增放行或禁用项。
- 无该配置时，已有配置、请求内容和转发行为保持兼容。
- 管理页面可编辑、保存、重新加载和 YAML 预览该设置；前端任何一次全量保存都不会丢失它。
- 新增的全局上游默认项设置区域默认折叠。
- 严格配置解析、配置 API、配置导入/导出边界与敏感信息处理遵循现有约束。
- Docker 内 `go test ./...`、`go vet ./...` 及 `go run ./cmd/webbuild -check` 均通过。

## 边界

- 本期只增加“全局、按上游格式”的注入，不移除或重命名现有的按 Provider / 路由 / 目标配置。
- 请求体采用既有浅合并模型；不实现深层 JSON Patch、模板变量替换或按模型名/路由名匹配规则。
- 仅对模型推理 POST（含视觉识别）生效。健康检测、模型目录、余额查询等管理或探测 HTTP 请求没有统一请求体协议，维持既有行为。
- 自定义字段的值仍是 JSON 值；请求头和请求体仍受已有安全黑名单及大小限制保护。
